# 1080p 图像通路与 Flash 验证记录

本记录对应 2026-10-02 的图像质量与帧缓存修复。早期接入纪要中的灰度抽样、720p 参数和未加载 SDC 的描述不代表当前源码。

## 已实现

- 传感器输出窗口 1920×1080 RAW10；DDR 保存每像素高 8 位，显示为原生 1080p 彩色图像。
- RAW 四像素打包按实际扫描顺序进入 DDR，读出的两个像素不再交换字节。
- BGGR 双像素双线缓存去马赛克，3×3 双线性插值，四边同色镜像延拓；控制信号与 RGB 一起延迟。
- 自动白平衡统计取线性 RGB，显示侧执行饱和增益与 sRGB 转换，防止线性 RAW 直接输出到显示器导致中间亮度偏暗。
- HDMI 的 CAM 行显示实际采集尺寸、传感器帧率和 DDR 完整帧写入率 WR；HDMI 行独立测量输出尺寸与刷新率。曝光 agent 的 AE 显示和控制仍保留。

HDMI 总时序为 2200×1125，像素时钟 148.75 MHz，因此实际刷新约 60.10 Hz。帧率为一秒计数，可能显示相邻整数。

## 分块及色块闪烁修复

原 `ddr_buffer.v` 固定 bank 间距 `0xE2000` 只有 925,696 字节，1920×1080 RAW8 一帧需要 2,073,600 字节，跨 bank 覆盖。现由 `frame_bank_manager.v` 按尺寸计算间距，4 KiB 向上对齐后再留 4 KiB 保护空间：

| bank | 起始地址 | 间距 |
|---|---:|---:|
| 0 | 0 | 2,080,768 (`0x1FC000`) |
| 1 | 2,080,768 | 同上 |
| 2 | 4,161,536 | 同上 |

读端在 DDR 读模块实际锁存地址的同一拍锁定完整帧，写端跳过被读端占用的 bank；读写切换同拍也遵守此约束。`frame_buffer.v` 将最大图像尺寸传给内部 DDR 模块。

## 验证与限制

RTL 回归均通过：RGGB/BGGR 三种图像的连续三帧逐像素及控制时序检查；256 输入灰度×6 增益的 RGB/sRGB 检查；带 valid 间隙的 1920×1080 采集及模式变化；OSD 数字、字形和图像透传；三 bank 非重叠、写快于读和同时切换压力测试。

```sh
python3 tests/video/run_video_tests.py   # 需要 Icarus Verilog；支持 IVERILOG/VVP/IVERILOG_LIB 环境变量
.script/build-iris
.script/sync-iris                      # 默认 JTAG bridge → SPI Flash
```

Efinity 2026.1 的 map、interface、pnr、pgm 全通过，实际加载项目 SDC。输入时钟先定义再应用 PHY/UART 延迟；跨 FIFO 的域使用异步时钟组。最终时序报告所列 setup/hold 余量均为正，最小 setup 余量仅 +0.001 ns（DDR IP 内部跨域 Gray 指针），不能由此推断实板长期稳定性。

用户在前一版实屏测得 CAM 1920×1080、30–31 fps，WR 30，HDMI 1920×1080、60 fps。摄像头原生 60 fps 尚未验证，也不能把 HDMI 重复显示同一帧算作 60 fps 采集。当前 HTS=1800、VTS=1150 没有达到目标；后续需核实传感器寄存器回读、时钟及 60 fps 初始化表。

## 2026-10-03：完整帧发布与曝光位域

继续检查发现两处实际接口错误，上一轮 bank 管理仿真只提供理想完成脉冲，未覆盖真实 DDR 写模块的输出，因此没有检出第一处问题。

1. `ddr_wr_buffer.v` 原 `bank_sw = burst_last`：`burst_last` 在最后一个 burst 的整个传输过程中保持高电平。bank 管理每拍都会据此发布和切换，既重复发布，也没有等待最后一段写完。现等待最后一个 W 数据拍与全部 B 响应完成，只输出一次完成脉冲。
2. `ae_ctrl.v` 曝光位域原为 `3e00=exp[11:8], 3e01=exp[7:0]`，传感器实际解码为 `{3e00[3:0],3e01,3e02[7:4]}`。512 半行被编码为 8192 半行，超出 VTS=1150 对应的 2289 半行上限。现为 `3e00=0, 3e01=exp[11:4], 3e02={exp[3:0],4'b0}`。保留曝光 agent 最新的手动按键调整方案。

新增回归均通过：真实 DDR 写模块的地址及像素顺序、最后一段 80 拍停顿、延迟 B 响应、连续三帧单次发布；真实曝光控制模块的 I2C group-hold、4 至 2289 半行范围和按键控制。临时恢复旧写法时，前者在只完成 256/320 个数据字、收到 1/3 个 B 响应时检出提前发布；后者检出 `0x220` 被写成 `0x2200`。

本轮使用 `/tmp/iris-quality-tools/video-timing-snapshot/iris_ws` 固定源码快照编译，避免公共 outflow 文件被并发构建改动。构建与烧录脚本支持 `IRIS_PROJ_DIR` 指定同一项目目录。最新实屏反馈确认画面正常、流畅，先前全屏闪白及队列迟滞已经消失；CAM/WR 为 1080p 30–31 fps、HDMI 60 fps。用户仍观察到发灰和曝光调整时色彩变化。

## 2026-10-03：色彩稳定和校准

原白平衡每帧重新估计，三位增益以 1/4 为一档。更改曝光时暗部偏置、高光截断和参与统计的场景比例会改变估计，容易出现色彩跳动。新版使用 Q8 十位增益（256 为 1 倍，范围 0.5–3 倍），启动稳定后校准一次并锁定；曝光按键与后续场景变化不再自动重写色彩增益。

白平衡统计扣除已校准黑电平，排除任一通道低于 12、高于 235 或最大通道超过最小通道三倍的像素。原始 RGB 总和继续用于原有曝光诊断。至少 4096 个合格像素、曝光稳定 8 个显示帧后进行校准，40 拍串行除法，结果只在垂直消隐应用。校准期间曝光改变会重新等待。

显示侧增加逐通道黑电平扣除、精细白平衡、保持黑白端点的适度 S 曲线及 1.25 倍色度增强；灰阶仍保持中性，负值及溢出饱和截断。三拍处理流水线把 HS/VS/DE 与 RGB 一起延迟。不更改已验证的 DDR 帧发布或传感器时钟参数。

| 按键 | 用途 |
|---|---|
| KEY0 / KEY1 | 降低 / 提高曝光，保留手动方案及长按重复 |
| KEY2 | 白平衡重新校准，校准后锁定 |
| KEY3 | 遮住镜头时测量每通道黑电平，平均值超过 64 则拒绝 |

Flash 启动后，先遮住镜头短按 KEY3，等待约 1 秒，再打开镜头，将白纸尽量填满画面，调整曝光使白纸不过曝，短按 KEY2。第四行显示 `WB CAL` / `WB LOCK` 和 `BL`（绿色通道黑电平）。看到 `WB LOCK` 后改变曝光应保持白平衡增益；传感器高光实际剪裁仍可能使过曝颜色失真。光源改变时可重新按 KEY2。校准值保存在 FPGA 寄存器中，掉电后重新校准；并未写入传感器非易失存储。

新增回归覆盖 256 输入等级 × 8 组 Q8 增益、黑电平边界、对比度/色度及同步；完整 1080p 统计量除法、锁定后曝光/场景变化、手动重校准、增益上下限、曝光变化重新等待、逐通道黑电平、亮帧拒绝、暗部/过曝/强偏色像素过滤、统计逐帧清零、校准状态 OSD。全部 RTL 回归通过。实屏色彩效果尚需此版 Flash 启动及上述校准后反馈；没有标定色卡和传感器色彩矩阵，不能据编译宣称达到消费级相机的色准。


色彩版 Efinity map/interface/pnr/pgm 全部通过；时序报告最小 setup +0.014 ns、hold +0.015 ns。固件保存于 `firmware/video-colour-20261003/`，RTL/构建日志、源码哈希和时序摘要保存于 `docs/validation/20261003-video-colour/`。

## 2026-10-03：原生 60 fps 诊断与时钟候选

重新连接下载 USB 后，含上述色彩处理的诊断版已经写入 W25Q64 Flash，并完成回读校验；用户重新配置启动后，UART 实板读回传感器 ID `CD6B`、1920×1080、HTS=1800、VTS=1150。传感器帧率与 DDR 完整帧写入率均为 30 fps，HDMI 为 60 fps，MIPI CLKOUT 每秒边沿计数为 21,231,365。此计数是包含可能的 LP 停钟的平均值，不能当作 HS 突发时钟或由此推算链路峰值带宽；CSI IP 配置中的 70 MHz 同样不能作为实测时钟。这些实测记录位于 `docs/validation/20261003-1080p60/baseline-*`。

诊断 UART 原来在同一请求高电平期间连续两拍递交数据，造成隔字节丢失；修复发送握手后，真实 UART 解码回归验证连续三行完整报文。新增传感器 32 个寄存器的一次完整快照回读，覆盖尺寸、HTS/VTS、两个 PLL、曝光与开流状态，并测试与曝光写入的仲裁。CLKOUT 每秒边沿使用 Gray 计数跨域测量，帧周期使用 100 MHz 核心时钟测量。

时钟候选 A 使用同一 SC431HAI 公共驱动的 27 MHz、四通道时钟配置值，保留线性模式和原生 1080p 窗口；开流命令移到窗口和时序配置完成之后。候选 A 的 RTL 回归以及 Efinity map/interface/pnr/pgm 全部通过，最小 setup +0.014 ns、hold +0.026 ns，已经写入 Flash 且回读校验成功。用户配置复位后，连续 12 份 UART 报文均回读原生 1920×1080、HTS=1800、VTS=1150，CAM/WR 均为 54 fps，帧周期 1,848,216–1,848,218 个核心时钟周期，实际 54.10617–54.10623 fps；HDMI 为 60–61 fps。候选 A 已提升采集率，但未达到 60 fps。原始报文与解码数据为 `candidate-a-uart.log/.json`。

构建及烧录新增失败即停止的 setup/hold 检查，烧录脚本要求日志出现 `Flash verify successful` 才报告完成。诊断首次编译发现 AE OSD 字符索引链导致 HDMI 时序不满足；改为并行常量区间译码后通过时序，回归检查全部 1920 个水平位置的字符和间隙映射。候选源码清单、构建、回归和烧录日志存于 `docs/validation/20261003-1080p60/`。

实板抓取命令：`python3 .script/read-video-status --seconds 15 --output <记录前缀>`。该脚本通过 `/dev/ttyUSB2`、115200 baud 保存原始 UART 与解码后的尺寸、帧率、字节时钟、帧周期；帧周期换算依赖板上 100 MHz 核心时钟。


候选 B 保持候选 A 的两个 PLL、原生输出窗口、VTS=1150 及手动曝光约束，依据实测周期把 HTS 从 1800 改为 1622（`320c=06, 320d=56`），预计 60.043 fps。此预测基于行周期与 HTS 成正比，需实板检查 CAM 与 WR、测得尺寸以及画面完整性。PLL 配置值参考 [OpenIPC SC431HAI 寄存器表](https://github.com/OpenIPC/openhisilicon/blob/main/libraries/sensor/hi3516cv6xx/smart_sc431hai/sc431hai_cfg.h)，只取时钟配置，保持 `3250=00` 线性模式。


用户确认候选 A 的实屏画面完整、流畅，无闪白、色块或分屏，OSD 实测 CAM 尺寸为 1920×1080。候选 B 的全部 RTL 回归以及 Efinity map/interface/pnr/pgm 已通过，最小 setup +0.014 ns、hold +0.026 ns；本次使用独立固定快照 `video-60-hts-b/iris_ws`，烧录与实测结果继续记录于同一验证目录。


## 2026-10-03：原生 1920×1080 / 60 fps 达成

候选 B 已写入板载 W25Q64 Flash 地址 0，最终 `Flash verify successful`，用户随后配置复位启动。连续 20 秒串口抓取获得 16 份完整报文，传感器寄存器保持原生 1920×1080、HTS=1622、VTS=1150；实测帧周期为 1,665,448–1,665,450 个 100 MHz 核心时钟周期，即 **60.04383–60.04390 fps**。CAM 与 DDR 完整帧写入率 WR 均为 60–61 fps，HDMI 此次采样均为 60 fps；偶尔 61 是非整数帧率的一秒计数结果。曝光按键调整期间仍保持这一帧周期。

用户确认最终版 OSD 实测 CAM 尺寸为 1920×1080，画面完整、流畅，没有闪白、色块或分屏。达成的是传感器原生采集约 60.044 fps，并已完成帧缓存写入验证。此前的 54 fps 候选以及 30 fps 诊断版均不是最终运行固件。
